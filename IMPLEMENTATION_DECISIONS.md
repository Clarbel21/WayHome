# WayHome safety and personalization refinement

Inspected baseline: `96d76f9`. Existing S0–S5, persisted Zustand safety state, simulated device adapter, Memory Garden store/IndexedDB, landmark editor, emergency dialogs, and regression tests were reviewed before editing.

## Decisions made before implementation

1. Keep S0–S5 and add a separate incident lifecycle: active → awaiting verification → resolved. Acknowledgment means receipt only. Requesting reset/resolution stays in S5; explicit caregiver verification checks person confirmation, connection, attachment observations, GPS confidence and outstanding scenario conditions. Closing an incident never changes connection/wear inputs or fabricates a wearer check-in. A new SOS cancels pending verification and takes precedence over every event. Full Reset Demo remains an explicitly labeled fictional fixture reset, is blocked during unresolved S5, and cannot bypass incident resolution. It preserves the selected attachment.
2. Add pure deterministic scenario rules with visible demonstration thresholds: deviation ≥100 m (only when GPS confidence ≥60%), inactivity ≥15 simulated minutes, ≥2 missed check-ins, and GPS confidence <60%. These trigger support/check-in states, never automatic police dispatch or AI emergency judgments. Restore/clear observations explicitly; do not assume acknowledgment repairs them. No wall-clock monitoring is introduced.
3. Add wristwatch, pendant, clothing-clip configurations with attachment-specific synthetic observations. Outputs are likely worn / possibly removed / not worn / unknown. Even “not worn” is an inference from simulated inputs, never guaranteed. Changing attachment clears observations to unknown. Keep the old boolean only as a compatibility-derived capability gate, not a user-facing assertion. Disconnection makes current wear knowledge unknown. Hardware assumptions are illustrative, not measured capabilities or claims about Memoket Gem.
4. Suggest optional activities by explicit caregiver activity choices/music notes and selected/completed/skipped history. Use transparent rules, not cognitive scores or automatic difficulty changes. Suggestions do not start activities and can be ignored. Preserve approval gates and safety pause.
5. Propose approved memory places as separate pending landmarks. Copy uploaded photo blobs so later memory deletion cannot remove a navigation photo. Navigation requires a separate explicit checkbox plus a simple reviewed instruction. Later memory edits/approval changes never silently change navigation approval. Existing landmarks stay intact.
6. Preserve hash routing, relative asset paths, Pages workflow, branding and browser-local storage. Merge legacy saved settings; legacy binary wear becomes unknown until new observation. Existing active S5 remains unresolved after migration.

## Validation plan

Test every rule at/below threshold, low-confidence deviation suppression, SOS while awaiting verification, acknowledgment vs resolution, stale verification attempts, device input preservation, each attachment/uncertain observation, refresh migration, optional recommendations, and separate photo/navigation approvals. Run all unit/browser tests, production build and a `/WayHome/` smoke test. Record final evidence and limitations below.

## Final validation and review

- `npm run build`: passed TypeScript and production bundling. Vite retains third-party `use client` warnings and reports the main bundle above 500 kB; these are non-fatal.
- `npm test`: **30 passed**. Tests cover rule boundaries, low-confidence deviation suppression, support-state priority, all three attachment classifiers/all four uncertainty outputs, acknowledgment vs resolution, preserved disconnected/removal observations, explicit person confirmation, new SOS invalidating pending verification, legacy migration and full demo-reset bypass prevention, plus existing safety/memory/name behavior.
- `CHROMIUM_PATH=/usr/bin/chromium npm run test:e2e`: **16 passed**. Includes the twelve previous flows updated for explicit incident verification and four new browser flows covering cross-tab SOS during verification, device faults, all scenario controls, attachment uncertainty, local-photo proposal/explicit approval/independent deletion survival, optional suggestions, mobile width and keyboard controls.
- Production build served under `/WayHome/`: passed routing, attachment refresh persistence, S5 fixture-reset guard, request/verification, optional suggestions, memory recognition and bundled assets; no runtime exceptions or local asset failures. Desktop and mobile screens inspected.
- Existing Pages workflow and Vite base configuration remain unchanged. No dependencies added. `original-backup` and its snapshot tag are not edited.

Known limitations: observations, thresholds, person confirmation and attachment sensors are fictional demo inputs, not validated hardware or real-world safety verification. No GPS/BLE/emergency service integration or cognitive scoring is added. Browser-local state/media does not sync between devices, and simultaneous same-origin tab writes still use last-write-wins. Independently copied navigation photos/landmarks are not included in Memory Library backups. Historic alert capacities remain unchanged. The production bundle size warning remains a future optimization opportunity.

## Follow-up: caregiver continuation after help is received

User testing showed that requiring healthy attachment/GPS readings before ending S5 prevented presentation users from proceeding after a caregiver confirmed help. Incident resolution is now separate from device/navigation verification. The existing strict `verifyIncident` remains for full device verification; the UI uses `resolveIncident` to record explicit person confirmation, preserve all fault inputs, and mark device review pending when needed. A review tied to the exact resolved incident permits local reminiscence in CHECK_IN; it never permits guidance or movement under inadequate inputs. New SOS/risk/device observations revoke this allowance. Acknowledgment remains receipt only. Tests cover the previously blocked offline/removed-device flow through completed Memory Garden activity and refresh, plus new-SOS interruption.

Validation for this follow-up: production build and **32 unit tests passed**; the full existing **22 browser tests passed**, followed by **5 focused SOS browser tests** including two additional cases for delayed hold timers and caregiver-dashboard confirmation with pending wear review. The production `/WayHome/` mobile flow from disconnected/removed → SOS → caregiver confirmation → completed memory also passed, with device readings preserved. SOS hold release now checks elapsed duration so a throttled browser timeout cannot discard a full two-second hold.

## Interactive check-in (October 2026)

Keep the six safety modes and existing incident verification gates. Add persisted check-in stages, response timestamps, and a distinct simulated family request lifecycle inside the existing store. A single application timer repeats once, then logs an unresolved check-in; the demo policy controls notification only. No timeout infers that someone is lost or contacts emergency services. Recognition advances only explicitly approved landmarks; rejection stops guidance. Caregiver acknowledgment and simulated response do not resolve an emergency or physical safety condition. Existing device and incident blockers continue to guard normal monitoring.

## Button logic audit (October 2026)

Audit the store actions as well as visible handlers: buttons must either perform a valid transition, offer a recovery route, or explain their disabled state. Preserve pending family requests across device and signal updates, deduplicate repeated answers/acknowledgments, and keep SOS independent. A caregiver's explicit check-in review uses the same recorded response action as the wearer; it cannot fabricate healthy device readings. Handover screens without an interactive family request must offer a way to create one. Help choices need a way back to the question. Route resets must not modify an active SOS snapshot. Memory actions must reject edits to paused, completed, or withdrawn content, including stale callbacks.
